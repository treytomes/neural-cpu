## Key Design Decisions

**Terminal.Gui v2 over Basic Console:**
Chose Terminal.Gui for the UI because:
- Professional appearance with frames and layouts
- Event-driven architecture matches our design
- Cross-platform TUI capabilities
- Rich widget library for future expansion

The v2 API differs significantly from v1 (event names, data binding), but provides better structure and maintainability.

**HALT as Interrupt Vector 0x00:**
Following CPU conventions where vector 0x00 is typically reserved for critical operations. HALT is processed at cycle boundaries, not immediately, which maintains deterministic behavior and allows the current cycle to complete.

**Hosting Integration Benefits:**
Using Microsoft.Extensions.Hosting provides:
- Standard .NET application patterns
- Built-in dependency injection
- Lifecycle management for components
- Easy testing with mock dependencies
- Configuration system integration

This positions the project to easily add more components (ALU, registers, memory) as services.

**Serilog for Structured Logging:**
Chose Serilog over built-in logging because:
- Excellent file sink with rolling/retention policies
- Structured logging with message templates
- Wide ecosystem of sinks (could add database, cloud logging later)
- Performance optimized for high-throughput scenarios

Rolling daily with size limits ensures logs don't fill the disk while maintaining enough history for debugging.

**Constructor Injection Over Service Locator:**
All components receive dependencies via constructor injection rather than requesting services. This makes dependencies explicit, improves testability, and follows SOLID principles.

## Insights & Observations

**TUI Event-Driven Nature Maps Well:**
The Terminal.Gui event model (button clicks, window closing) naturally maps to our event bus architecture. Both use the Observer pattern, creating consistency across the codebase.

**Cleanup is Critical for Background Threads:**
The initial issue where the process hung after Esc highlighted the importance of proper cleanup. Now we have:
- Window Closing event → Shutdown()
- Shutdown() → Clock.Stop() with timeout
- Clock.Stop() → Task.Wait() + Dispose()
- Host.Dispose() → All hosted services stopped

Multiple layers ensure clean shutdown even if one layer fails.

**Logging Reveals Hidden Behavior:**
Adding logging to the Clock immediately showed the timing of interrupt processing and the flow of start/stop operations. This will be invaluable when debugging multi-component interactions later.

**Dependency Injection Makes Testing Possible:**
Before: components created their own dependencies (tight coupling)
After: components receive dependencies via constructor (loose coupling)

This means we can now:
- Mock the event bus for unit tests
- Test Clock in isolation
- Verify interrupt handling without running the full TUI

**Records for Events Were the Right Choice:**
Converting event types to records dramatically reduced boilerplate while adding immutability guarantees. Primary constructors make them concise to define and use.

## Questions & Uncertainties

**Performance of Event Bus:**
With all clock phases being published as events, will the event bus become a bottleneck at high frequencies? Should we batch events or use a more efficient pub/sub mechanism?

**Logging Volume at High Frequencies:**
If the clock runs at 1 KHz or higher, and we log each phase change, will we overwhelm the file system? May need to:
- Add log level filters for different components
- Use buffered logging sinks
- Make debug logging conditional on frequency

**TUI Refresh Rate:**
The TUI updates on every clock event. At high frequencies, will Terminal.Gui updates cause performance issues? May need:
- Rate limiting on UI updates
- Buffered event log updates
- Separate update thread

**Component Startup Order:**
Currently, all components start simultaneously when the host starts. Do we need:
- Explicit startup ordering?
- Dependencies between components (Clock starts before ALU)?
- Initialization phases?

**Testing Strategy:**
Should we:
- Unit test each component in isolation?
- Integration test via the event bus?
- Create a headless test harness separate from the TUI?

The DI setup makes all of these possible, but we need to decide on the testing approach.
